## Feature 1: OpenTelemetry Observability

**Plan Document:** [`opentelemetry-observability-plan.md`](opentelemetry-observability-plan.md)
**Effort:** 10-15 hours
**Test Count:** 30-40 tests
**Files Created:** 15-20 files
**Files Modified:** 3 files

### Purpose

Enable comprehensive distributed tracing for Pagent using industry-standard OpenTelemetry. Allows visualization of multi-agent workflows, performance monitoring, cost tracking, and integration with Jaeger, Zipkin, Datadog, New Relic, Langfuse, and Langsmith.

### Key Components

1. **TelemetryManager (Singleton)**
   - Initialize OpenTelemetry SDK
   - Create and manage spans
   - Register exporters (Console, OTLP, Jaeger, Zipkin)
   - Context propagation

2. **Span Wrapper**
   - Fluent API for span operations
   - Attribute setting
   - Event logging
   - Exception recording
   - Status management

3. **Automatic Instrumentation**
   - Agent operations (prompt, stream, executeTool)
   - LLM provider calls
   - Tool execution
   - Guard checks
   - Middleware processing
   - Workflow orchestration (Pipeline, Chain)

4. **Exporters**
   - ConsoleExporter (development debugging)
   - OTLPExporter (generic HTTP/gRPC)
   - JaegerExporter (Jaeger backend)
   - ZipkinExporter (Zipkin backend)

### Implementation Phases

- **Phase 1** (3-4h): Core infrastructure with console exporter
- **Phase 2** (3-4h): Agent integration with automatic instrumentation
- **Phase 3** (2h): Workflow integration (Pipeline, Chain)
- **Phase 4** (2-3h): Production exporters (OTLP, Jaeger, Zipkin)
- **Phase 5** (1-2h): Documentation and examples

### API Examples

```php
// Console debugging
telemetry_console(verbose: true);
agent('assistant')->telemetry(true)->prompt('Hello');

// Jaeger integration
telemetry_jaeger('http://localhost:14268/api/traces');
agent('researcher')->telemetry(true)->prompt('Research...');

// Multi-agent workflow tracing
telemetry_otlp('http://localhost:4318/v1/traces');
pipeline('content')
    ->step('research', agent('researcher'))
    ->step('write', agent('writer'))
    ->run('Write article');
```

### Semantic Conventions

Follows OpenTelemetry Semantic Conventions for GenAI:
- `gen_ai.system` - Provider (anthropic, openai, ollama)
- `gen_ai.request.model` - Model name
- `gen_ai.usage.input_tokens` - Input token count
- `gen_ai.usage.output_tokens` - Output token count
- `agent.name` - Agent identifier
- `tool.name` - Tool being executed
- `guard.name` - Guard being checked

## Feature 2: Cost & Token Usage Tracking

**Plan Document:** [`cost-token-tracking-plan.md`](cost-token-tracking-plan.md)
**Effort:** 4-6 hours
**Test Count:** 64 tests
**Files Created:** 20 files
**Files Modified:** 1 file

### Purpose

Enable developers to monitor LLM API costs, enforce budgets, track usage per agent/session, and export data for analysis. Essential for production deployments and cost control.

### Key Components

1. **UsageTracker (Singleton)**
   - Track usage records from agent interactions
   - Set budgets (agent-level, session-level, global)
   - Aggregate statistics (by agent, session, provider, model)
   - Export data (JSON, CSV)
   - Warning and record callbacks

2. **UsageRecord (Value Object)**
   - Immutable record of single LLM interaction
   - Token counts (input, output, total)
   - Cost calculation
   - Agent name, session ID, metadata

3. **ProviderPricing (Static)**
   - Accurate pricing for Anthropic, OpenAI, Ollama
   - Pricing as of January 2025
   - Calculate costs based on model and token usage
   - Support for custom pricing

4. **Storage Adapters**
   - MemoryStorage (default, in-memory)
   - SqliteStorage (persistent, historical data)
   - UsageStorageInterface (extensible)

5. **Budget Enforcement**
   - Soft warnings at configurable threshold (default 80%)
   - Hard limits with BudgetExceededException
   - Per-agent, per-session, and global budgets

6. **Export Capabilities**
   - JsonExporter - Full data with metadata
   - CsvExporter - Spreadsheet-compatible format

### Implementation Phases

- **Phase 1** (2h): Foundation (UsageRecord, ProviderPricing, UsageTracker)
- **Phase 2** (1h): Budget enforcement and exceptions
- **Phase 3** (1.5h): Storage adapters and exporters
- **Phase 4** (1h): Integration tests and workflow examples
- **Phase 5** (0.5h): Documentation and examples

### API Examples

```php
// Basic tracking with budget
agent('assistant')
    ->trackUsage(['budget' => 10.00, 'warn_at' => 0.8])
    ->prompt('Hello');

$usage = agent('assistant')->getUsage();
// ['total_requests' => 1, 'input_tokens' => 10, 'cost' => 0.00045]

// Session-level tracking
agent('chatbot')
    ->sessionId('user-123')
    ->trackUsage()
    ->sessionBudget(5.00)
    ->prompt('Question');

// Global analytics
$summary = UsageTracker::instance()->summary();
$byAgent = UsageTracker::instance()->byAgent();
$bySession = UsageTracker::instance()->bySession();

// Export to CSV
UsageTracker::instance()->export('csv', 'usage-report.csv');

// Warning callback
UsageTracker::instance()->onWarning(function($scope, $id, $percentage) {
    echo "⚠️  Budget at " . round($percentage * 100) . "%\n";
});
```

## Feature 3: MCP Server Support

**Plan Document:** [`mcp-server-support-plan.md`](mcp-server-support-plan.md)
**Effort:** 6-8 hours
**Test Count:** 88-109 tests
**Files Created:** 12-15 files
**Files Modified:** 1 file

### Purpose

Enable Pagent to connect to Model Context Protocol (MCP) servers and automatically discover/use external tools. Provides access to the growing MCP ecosystem (filesystem, GitHub, databases, APIs) without reimplementing tools.

### Key Components

1. **McpClient**
   - JSON-RPC protocol implementation
   - Tool discovery from MCP servers
   - Tool execution via MCP
   - Connection lifecycle management

2. **Transport Layer**
   - StdioTransport (process-based MCP servers)
   - HttpTransport (HTTP-based MCP servers)
   - TransportInterface (extensible)

3. **McpServer Configuration**
   - Factory methods (stdio, HTTP)
   - fromConfig() for configuration arrays
   - Environment variable support

4. **McpTool Wrapper**
   - Implements ToolInterface
   - Automatic schema conversion (MCP → Anthropic/OpenAI)
   - Parameter validation
   - Seamless integration with existing tool system

5. **Agent Integration**
   - `mcpServer(name, config)` - Auto-discover all tools
   - `mcpTools(name, toolNames, config)` - Selective import
   - Automatic cleanup on destruction

### Implementation Phases

- **Phase 1** (3-4h): Core MCP client and transport layer
- **Phase 2** (1-2h): Agent integration methods
- **Phase 3** (2-3h): Testing (mock servers, real servers)
- **Phase 4** (1h): Documentation and examples

### API Examples

```php
// Automatic tool discovery (stdio)
agent('assistant')
    ->mcpServer('filesystem', [
        'type' => 'stdio',
        'command' => 'npx -y @modelcontextprotocol/server-filesystem /tmp',
    ])
    ->prompt('List files in current directory');

// HTTP transport
agent('assistant')
    ->mcpServer(McpServer::http(
        name: 'api-tools',
        url: 'http://localhost:3000/mcp',
    ))
    ->prompt('Query the database');

// Multiple servers
agent('assistant')
    ->mcpServer('filesystem', ['type' => 'stdio', ...])
    ->mcpServer('github', ['type' => 'stdio', ...])
    ->prompt('Read local file and create GitHub issue');

// Selective tool import
agent('assistant')
    ->mcpTools('filesystem', ['read_file', 'write_file'], [...])
    ->prompt('Read config and write output');

// Mixed with built-in tools
agent('assistant')
    ->tool(new \Pagent\Tools\WebFetch())
    ->tool('calculate', 'Add', fn($a, $b) => $a + $b)
    ->mcpServer('filesystem', [...])
    ->prompt('Fetch API, calculate, save result');
```

## Looking Ahead: v0.8.0 Preview

### Events/Hooks System (Breaking Change)

**Plan:** [`events-hooks-system-plan.md`](events-hooks-system-plan.md)
**Effort:** 6-8 hours
**Status:** Planned

While v0.7.0 introduces observability through **manual span creation** (calling `TelemetryManager::instance()->startSpan()` throughout Agent.php), v0.8.0 will refactor this to an **event-driven architecture**.

#### Key Changes

1. **Event-Driven Observability**
   - Fire typed events at all Agent lifecycle points
   - `BeforePromptEvent`, `AfterLLMResponseEvent`, `ToolExecutedEvent`, etc.
   - 18 fully-typed event classes

2. **TelemetryEventBridge**
   - Listener that auto-creates spans from events
   - Replaces manual `startSpan()` calls
   - Cleaner separation of concerns

3. **Hybrid Listener Pattern**
   - Both closure and class-based listeners
   - Follows existing Guard pattern
   - Priority system and propagation control

4. **Agent API**
   ```php
   agent('bot')
       ->on('after_prompt', fn($e) => Log::info('Done'))
       ->once('tool_executed', $handler)
       ->prompt('Hello');
   ```

#### Why This Matters

The v0.7.0 manual span creation works but **tightly couples** observability to core agent logic. Events provide:
- **Extensibility**: Users can hook into agent lifecycle
- **Decoupling**: Telemetry is a listener, not embedded in Agent
- **Testability**: Easier to test without TelemetryManager
- **Flexibility**: Multiple observers can listen to same events

#### Migration Path

v0.8.0 will be a **breaking change** but with backward compatibility:
- Both manual and event-driven spans work during transition
- Feature flag to enable/disable TelemetryEventBridge
- Full migration guide provided

**Impact:** v0.7.0 implementers should be aware this refactoring is coming. The good news: v0.7.0's TelemetryManager, Span classes, and exporters remain unchanged - only how spans are **created** will change (from manual calls to event-driven).
